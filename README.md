# ЧАСТЬ I: БЭКЕНД-ИНФРАСТРУКТУРА (PYTHON / FASTAPI)

## 1. Системная архитектура бэкенда

### 1.1 Сетевая инфраструктура и деплой
*   **Cloudflare (Proxy Mode - Оранжевое облако):**
    *   **Скрытие IP:** Запросы маршрутизируются через прокси-серверы Cloudflare, скрывая реальный IP-адрес хостинга от DDoS-атак и сканирования портов.
    *   **WAF (Web Application Firewall):** Автоматическая фильтрация вредоносного трафика, блокировка известных эксплойтов и подозрительных юзер-агентов.
    *   **Rate Limiting:** Ограничение частоты запросов на уровне DNS для публичного эндпоинта `/api/v1/leads` (например, максимум 3 запроса в минуту с одного IP) для превентивной защиты от спама.
*   **Nginx (Reverse Proxy и Веб-сервер):**
    *   **Раздача фронтенда:** Локальный Nginx на сервере напрямую отдает собранный статический бандл Vue 3 (HTML, CSS, JS). Конфигурация включает правило `try_files $uri $uri/ /index.html;` для корректной работы Vue Router.
    *   **Проксирование API:** Запросы на `/api/` перенаправляются на локальный порт Python-приложения (например, `http://127.0.0.1:8000`).
    *   **Проксирование медиафайлов (MinIO):** Запросы на `/media/` проксируются на порт локального S3-хранилища MinIO (`http://127.0.0.1:9000`), автоматически подставляя имя бакета `agroprom-media`. Это исключает необходимость открывать порты MinIO наружу и гарантирует, что все медиафайлы отдаются через Nginx под защитой Cloudflare с возможностью кэширования статики на 24 часа.
    *   **Безопасность заголовков:** Настройка заголовков безопасности, таких как HSTS, `X-Frame-Options: DENY` (защита от Clickjacking) и `Content-Security-Policy`.

### 1.2 Архитектура бэкенда (Python / FastAPI)
*   **Асинхронный движок (Asyncio):** Использование FastAPI в асинхронном режиме позволяет обрабатывать большое количество одновременных соединений (включая входящие вебхуки от Telegram) без блокировки основного потока выполнения.
*   **Работа с СУБД:** СУБД PostgreSQL в связке с асинхронным драйвером и ORM SQLAlchemy 2.0 (использование `asyncSession`).
*   **Контроль версий базы данных (Миграции через Alembic):** Отказ от автоматического создания таблиц при старте. Все изменения структуры БД описываются декларативно в моделях SQLAlchemy и накатываются на сервер в виде пошаговых миграций с помощью утилиты Alembic.
*   **Абстракция объектного хранилища (MinIO / S3):** Для хранения медиафайлов (фотографий техники) используется S3-совместимый протокол (через библиотеку `boto3`). Физически файлы хранятся в локальном контейнере **MinIO** на том же сервере с отключенной веб-панелью для минимизации потребления ресурсов и максимальной безопасности.
*   **Фоновые задачи (Background Tasks):** Для отправки уведомлений в Telegram-бот используется встроенный в FastAPI механизм BackgroundTasks. Бекенд мгновенно сохраняет заявку в БД и отдает клиенту ответ 200 OK, а отправка сетевого запроса к серверам Telegram выполняется асинхронно в фоне, не блокируя пользователя.
*   **Многофункциональный кэш-слой (Redis):** Внутрисистемная память Redis используется расширенно: для лимитирования запросов (Rate Limiting), временного кэширования ресурсоемких выборок каталога техники (`machines`), хранения временных сессий, распределенных блокировок и буферизации фоновых процессов.
*   **Валидация и парсинг (Pydantic):** Строгая валидация входящих и выходящих данных с помощью схем Pydantic.
*   **Конфигурация и секреты (Pydantic Settings):** Все конфигурационные данные (токен бота, доступы к БД, секретный ключ JWT, доступы к MinIO) хранятся в изолированном файле `.env`. Чтение и валидация переменных окружения осуществляются через класс Settings библиотеки `pydantic-settings`, предотвращая запуск приложения с некорректными или отсутствующими параметрами.

### 1.3 Спецификация безопасности API

#### А. Публичная форма обратного звонка
*   **Интеллектуальная валидация номера телефона:** Вместо базовых регулярных выражений на этапе парсинга Pydantic-схемой применяется библиотека `phonenumbers` (порт Google Libphonenumber). Проводится проверка не только формата записи, но и существования кода оператора и страны для автоматического отсечения заведомо вымышленных и нераспределенных диапазонов цифр.
*   **Санитаризация текстовых полей:** Принудительное удаление HTML-тегов, скриптов и спецсимволов из текстовых полей перед сохранением данных для предотвращения XSS-инъекций.
*   **Предотвращение дублирования (Активные заявки):** При поступлении нового запроса выполняется предварительный поиск в БД по номеру телефона среди записей со статусами `NEW` или `IN_PROGRESS`. При обнаружении активной заявки новая запись в БД не создается, а клиенту возвращается статус-ответ `already_exists`, который Vue отображает в виде дружелюбного сообщения. Это защищает базу от дублирования, а Telegram-канал менеджеров — от повторного шума.
    *   *Защита на уровне СУБД (Частичный уникальный индекс):* Для предотвращения гонки запросов (Race Condition) на уровне базы данных PostgreSQL создан частичный уникальный индекс `uniq_active_phone`. Это физически исключает создание дубликата активной заявки, даже если два параллельных запроса обойдут валидацию кода в одну и ту же миллисекунду.
*   **Капча (Turnstile):** Проверка токена Cloudflare Turnstile на стороне бекенда перед фиксацией лида для блокирования автоматизированных бот-сетей.
*   **Многоуровневый Rate Limiting (Redis):** Ограничение частоты отправки запросов с одного IP-адреса и масок подсетей с использованием Redis. Реализуется алгоритм Token Bucket для защиты от целенаправленного ручного спама и перебора номеров.

#### Б. Авторизация администратора (JWT + Cookie с механизмом Rolling Refresh)
Для обеспечения максимальной безопасности сессий администратора применяется раздельная двухтокенная схема авторизации:
1.  **Access Token (JWT в ОЗУ клиента):**
    *   **Время жизни:** Краткосрочный (15 минут).
    *   **Передача:** Возвращается сервером в теле JSON-ответа при успешной авторизации и сохраняется Vue-приложением в оперативной памяти (в стейте Pinia). Он прикрепляется к каждому HTTP-запросу в заголовке `Authorization: Bearer <token>`.
    *   **Защита:** Access Token не хранится в LocalStorage или SessionStorage, что исключает его компрометацию через прямое чтение постоянного хранилища браузера после завершения сессии или закрытия вкладки.
2.  **Refresh Token (HttpOnly Cookie на клиенте):**
    *   **Время жизни:** Долгосрочный (7 дней).
    *   **Передача:** Записывается сервером в браузер через заголовок `Set-Cookie` с флагами `HttpOnly`, `Secure` и `SameSite=Strict`. Браузер автоматически прикрепляет эту куку к запросам обновления сессии (`POST /api/refresh`).
    *   **Защита уровня HttpOnly:** Флаг `HttpOnly` полностью блокирует доступ к куке со стороны JavaScript. Никакой вредоносный скрипт на клиенте не может прочитать этот токен через `document.cookie`.
    *   **Защита уровня Secure (HTTPS):** Флаг `Secure` гарантирует, что браузер передаст эту куку только по зашифрованному HTTPS-соединению, исключая перехват в открытой сети (защита от MITM-атак).
    *   **Защита SameSite=Strict:** Предотвращает уязвимость CSRF (межсайтовая подделка запроса), блокируя отправку куки при запросах со сторонних сайтов.
3.  **Хеширование паролей (Argon2id):**
    *   Для обеспечения криптостойкости паролей администраторов на бэкенде применяется алгоритм **Argon2id** (рекомендованный OWASP и побеждавший на Password Hashing Competition). Данный алгоритм обеспечивает лучшую на текущий момент защиту от брутфорса, в том числе с использованием графических процессоров (GPU) и специализированных интегральных схем (ASIC), за счет контролируемого использования ресурсов процессора и оперативной памяти.
4.  **Механизм скользящей сессии (Rolling Refresh Tokens):**
    *   Для обеспечения комфортного UX и надежной защиты применяется концепция «скользящего» токена. При каждом обновлении сессии через `/api/refresh` (раз в 15 минут) бекенд проверяет старый Refresh-токен, выдает новый короткий Access-токен и **перевыпускает** долгосрочный Refresh-токен, сдвигая его срок жизни еще на 7 дней вперед.
    *   **Результат:** Если менеджер заходит в админку хотя бы раз в неделю, его сессия продлевается автоматически и бесконечно. Если менеджер не проявляет активности более 7 дней (например, ушел в отпуск), Refresh-токен окончательно сгорает, и при следующем визите система безопасно потребует повторный ввод пароля.
5.  **Ролевая модель доступа (RBAC):**
    *   В JWT-токен пользователя записывается его роль (`SUPERADMIN`, `EDITOR`, `MANAGER`), на основе которой бэкенд строго разграничивает доступ к эндпоинтам:
        *   `SUPERADMIN` (Главный администратор): Полный доступ ко всем ресурсам (управление техникой, заявками, пользователями).
        *   `EDITOR` (Редактор контента): Доступ только к CRUD-операциям над таблицей техники (`machines`).
        *   `MANAGER` (Менеджер по продажам): Доступ только к чтению и обновлению входящих заявок (`leads`).
    *   *Замечание для защиты:* Данная архитектура предусматривает масштабирование ролевой модели и добавление новых типов пользователей без необходимости перепроектирования схемы авторизации.
6.  **Унифицированная пагинация и фильтрация (Аудит):**
    *   Все списочные эндпоинты бэкенда (`GET /leads/`, `GET /machines/`, `GET /audit/`) поддерживают строгую пагинацию (параметры `limit` и `offset`). Ответы оборачиваются в универсальную схему `PaginatedResponse`, содержащую метаданные об общем числе записей (`total`) для корректной отрисовки страниц во Vue 3.
    *   Суперадминистратору предоставлен защищенный эндпоинт `GET /api/v1/audit/` для просмотра журнала системного аудита в реальном времени с поддержкой постраничного вывода и гибких фильтров по администратору (`user_id`), типу действия (`action`) и типу измененного объекта (`entity_type`).

#### В. Защита мутирующих запросов панели администратора
Ввиду того, что административная панель представляет собой классическое веб-приложение (SPA Vue 3), от сложного алгоритма HMAC-подписи решено отказаться во избежание overengineering'а. Вместо этого безопасность обеспечивается современными веб-стандартами:
1.  **Защитный канал (HTTPS/TLS):** Полностью берет на себя защиту от перехвата и модификации (Data Tampering) запросов в сети.
2.  **Защита от подделки межсайтовых запросов (CSRF):** Достигается за счет использования флага `SameSite=Strict` для HttpOnly куки и строгой валидации CORS (разрешены запросы только с доверенных доменов).
3.  **Защита от дублирования/Replay:** Решается использованием короткоживущих JWT и логической валидацией текущего состояния записей в БД (например, бекенд вернет ошибку, если попытаться изменить статус заявки, которая уже закрыта).

### 1.4 Интеграция с Telegram-ботом
*   **Двустороннее управление:**
    *   **Оповещение:** При создании нового лида бекенд отправляет сообщение в рабочий чат менеджеров.
    *   **Интерактивные Inline-кнопки:** Сообщение в Telegram содержит кнопки «Взять в работу» и «Завершить».
    *   **Оптимистическая блокировка лидов (Защита от гонки состояний):** Чтобы предотвратить ситуацию, когда два менеджера одновременно нажимают кнопку «Взять в работу» на одном и том же сообщении, обновление статуса заявки в СУБД производится атомарно с жестким логическим условием: `UPDATE leads SET status = 'IN_PROGRESS', updated_at = NOW() WHERE id = :id AND status = 'NEW'`. Если запрос затронул 0 строк, бэкенд фиксирует конфликт (лид уже был обработан другим сотрудником), прерывает операцию и возвращает предупреждение.
    *   **Webhook-архитектура:** Нажатие на кнопку в Telegram отправляет callback-запрос на эндпоинт бэкенда `/api/tg/webhook`. Бэкенд принимает этот запрос, обновляет статус лида в базе данных PostgreSQL и редактирует исходное сообщение в Telegram для отображения актуального статуса заявки (меняет кнопку на текст «В работе у @username»).

### 1.5 Стратегия резервного копирования и обслуживания (Backup & Maintenance)
Для обеспечения непрерывности бизнес-процессов, защиты от аппаратных сбоев на сервере и минимизации рисков потери критически важных данных в системе реализована регулярная стратегия обслуживания:
*   **Автоматический дамп Базы Данных (PostgreSQL):** Раз в сутки в автоматическом режиме с помощью планировщика выполняется резервное копирование структуры и данных базы данных с помощью стандартной утилиты `pg_dump` с последующим архивированием (`gzip`).
*   **Резервное копирование медиафайлов (MinIO):** Раз в сутки запускается автоматический скрипт синхронизации медиа-бакетов MinIO (фотографии техники), обеспечивающий консистентность файлов и записей в БД.
*   **Автоматическая ротация логов аудита в СУБД:** Каждую ночь перед созданием бэкапа на уровне PostgreSQL выполняется автоматическая очистка таблицы логов от записей старше 90 дней (через интервальный запрос `DELETE WHERE timestamp < NOW() - INTERVAL '90 days'`). Это предохраняет диск СУБД от переполнения и оптимизирует скорость работы поисковых индексов.
*   **Политика хранения и ротации бэкапов:** Все созданные резервные копии шифруются и сохраняются во внешнее изолированное хранилище с глубиной хранения (Retention) 30 дней.

### 1.6 Концептуальная схема Базы Данных (PostgreSQL)

*   **Таблица `users` (Администраторы):**
    *   `id` (UUID, primary key) — *Уникальный идентификатор пользователя в формате UUIDv4. Генерируется на стороне приложения для обеспечения максимальной криптостойкости и защиты от подбора ID перебором.*
    *   `username` (String, unique, indexed) — *Уникальное имя пользователя (логин) для авторизации в системе. Ограничено 50 символами и проиндексировано для быстрого поиска при авторизации.*
    *   `password_hash` (String) — *Криптографический хэш пароля администратора, сгенерированный с использованием современного алгоритма Argon2id. Прямое хранение паролей в чистом виде полностью исключено.*
    *   `role` (Enum: `SUPERADMIN`, `EDITOR`, `MANAGER`) — *Уровень прав доступа пользователя в системе. Определяет доступ к эндпоинтам API на основе ролевой модели (RBAC).*
    *   `is_active` (Boolean) — *Флаг активности учетной записи. Позволяет мгновенно заблокировать пользователя (отозвать сессию) без физического удаления его записи из базы данных.*

*   **Таблица `machines` (Карточки сельхозтехники):**
    *   `id` (Integer, primary key) — *Уникальный последовательный идентификатор записи в базе данных (автоинкрементный первичный ключ).*
    *   `title` (String, indexed) — *Название модели техники (ограничено 255 символами). Проиндексировано для быстрой фильтрации и поиска в каталоге.*
    *   `description` (Text, nullable) — *Подробное текстовое описание сельскохозяйственной техники. Поддерживает форматированный текст без ограничения по длине.*
    *   `specifications` (JSONB) — *Набор технических характеристик техники в гибком формате JSONB (например, мощность, вес, габариты). Позволяет хранить разнородные спецификации для разных типов машин без изменения схемы СУБД.*
    *   `price` (Numeric, nullable) — *Стоимость техники. Использует точный числовой тип данных `Numeric(10,2)` для избежания ошибок округления, свойственных числам с плавающей точкой (float).*
    *   `image_url` (String, nullable) — *URL-адрес изображения. Вместо локального пути хранится URL-адрес объекта, проксируемый Nginx из локального MinIO бакета.*
    *   `created_at` (DateTime) — *Дата и время создания карточки товара. Хранится с временной зоной (timezone-aware UTC) для точного ведения хронологии.*

*   **Таблица `leads` (Заявки на обратный звонок):**
    *   `id` (Integer, primary key) — *Уникальный последовательный идентификатор заявки (автоинкрементный первичный ключ).*
    *   `client_name` (String) — *Имя клиента, оставившего заявку (ограничено 100 символами, санитаризировано от вредоносных HTML-тегов/XSS на этапе API-валидации).*
    *   `client_phone` (String, indexed) — *Номер телефона клиента. Хранится в стандартизированном международном формате E.164 (например, +79991234567) и проиндексирован для быстрого поиска дубликатов.*
    *   `processed_by` (String, nullable) — *Имя менеджера (например, @username), взявшего заявку в работу через Telegram или админку. Позволяет выводить имя ответственного прямо в интерфейсе Vue.*
    *   `status` (Enum: `NEW`, `IN_PROGRESS`, `DONE`) — *Текущий статус обработки лида. Обновление статуса защищено атомарной логикой (оптимистичной блокировкой) для избежания конфликтов между менеджерами.*
    *   `created_at` (DateTime) — *Дата и время создания заявки с временной зоной (UTC) для фиксации точного времени обращения.*
    *   `updated_at` (DateTime) — *Дата и время последнего изменения заявки с временной зоной (UTC). Обновляется автоматически при смене статуса или назначении менеджера.*
    *   *Ограничение уникальности СУБД:* `CREATE UNIQUE INDEX uniq_active_phone ON leads(client_phone) WHERE status IN ('NEW', 'IN_PROGRESS');` — *данный частичный индекс блокирует дублирование лидов на уровне PostgreSQL в случае параллельных запросов-гонок.*

*   **Таблица `audit_logs` (Журнал аудита действий):**
    *   `id` (Integer, primary key) — *Уникальный последовательный идентификатор записи аудита (автоинкрементный первичный ключ).*
    *   `user_id` (UUID, foreign key, nullable) — *Внешний ключ, связывающий лог с администратором из таблицы `users`. Если действие совершено гостем или ботом — устанавливается `null`. Защищен каскадным правилом `ondelete="SET NULL"` для предотвращения нарушения целостности при удалении пользователей.*
    *   `action` (String, indexed) — *Тип совершенного действия в системе (например, `CREATE_MACHINE`, `UPDATE_PRICE`, `CHANGE_LEAD_STATUS`). Проиндексировано для быстрой фильтрации логов в админке.*
    *   `entity_type` (String) — *Тип измененного системного объекта, к которому относится действие (например, `lead`, `machine`).*
    *   `entity_id` (Integer) — *Физический идентификатор (id) объекта, над которым было совершено действие.*
    *   `timestamp` (DateTime, indexed) — *Дата и время фиксации лога с временной зоной (UTC). Проиндексировано для быстрой сортировки хронологии действий менеджеров и автоматики.*

## 4. Конфигурация Nginx / Nginx Proxy Manager (NPM)

Nginx работает как единая точка входа (API Gateway) для всей системы. Все запросы на домен (например, `agromachines.chabupelik.su`) проксируются по защищенному SSL-соединению (порт `443`), исключая прямое обращение внешних клиентов к портам Docker-контейнеров.

Пример подключения собранного фронтенда через `volumes`:
```yaml
volumes:
  - /home/chabupelik/AgroMachines/frontend/dist:/var/www/agroprom/frontend
```

Ниже представлен полный Nginx-конфиг для вкладки **Advanced** (Custom Nginx Configuration) в панели управления Nginx Proxy Manager:

```nginx
# 1. РАЗДАЧА СТАТИКИ ФРОНТЕНДА (Vue 3 / Vite)
location / {
    # Путь внутри контейнера NPM, куда примонтирована папка сборки (dist) фронтенда
    root /var/www/agroprom/frontend;
    index index.html;
    
    # КРИТИЧЕСКИ ВАЖНО ДЛЯ SPA (Vue Router):
    # Если пользователь запрашивает конкретный URL (например, /admin или /machines), 
    # Nginx не найдет такой папки на диске. Правило try_files велит серверу перенаправить 
    # запрос на index.html, где Vue Router перехватит управление и сам отрисует нужную страницу.
    # Без этого правила при перезагрузке страницы /admin пользователь будет получать ошибку 404.
    try_files $uri $uri/ /index.html;
    
    # Агрессивное кэширование статических файлов сборки (JS, CSS, шрифты, иконки)
    # Позволяет браузеру клиента сохранять файлы локально на 1 год, обеспечивая мгновенный запуск сайта при повторных визитах
    location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff|woff2|ttf|eot)$ {
        expires 1y;
        add_header Cache-Control "public, max-age=31536000, immutable";
        access_log off;
    }
}

# 2. МАРШРУТ ДЛЯ API (FastAPI)
location /api/ {
    # Проксируем все запросы с префиксом /api/ на внутренний IP докер-хоста (порт 8000)
    proxy_pass http://172.17.0.1:8000/api/;
    
    # Передача реальных заголовков клиента, чтобы FastAPI корректно логировал IP и HTTPS протокол
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    
    # Разрешаем загрузку тяжелых файлов (картинок техники) до 50 МБ
    client_max_body_size 50M;
    
    # Отключаем буферизацию для мгновенной отдачи ответов API клиенту
    proxy_buffering off;
}

# 3. МАРШРУТ ДЛЯ КАРТИНОК (Проксирование в S3 MinIO)
location /media/ {
    # Скрыто перенаправляет запрос /media/photo.jpg в бакет /agroprom-media/photo.jpg на порт 9000
    proxy_pass http://172.17.0.1:9000/agroprom-media/;
    
    # Специфичные заголовки для корректной авторизации S3-запросов со стороны MinIO
    proxy_set_header Host $http_host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    
    # Буферизация и кэширование статических изображений на уровне Nginx для снижения нагрузки на диск сервера
    proxy_buffering on;
    proxy_cache_valid 200 24h;
    expires 24h;
    add_header Cache-Control "public, no-transform";
}

```

### Разбор параметров конфигурации Nginx:
*   `proxy_pass`: Перенаправляет запрос на указанный адрес. `172.17.0.1` — это стандартный IP-адрес шлюза (docker0) хоста в Docker-окружении, что позволяет Nginx вне Docker безопасно общаться с контейнерами на localhost.
*   `proxy_set_header`: Заменяет или добавляет заголовки HTTP-запроса перед отправкой бэкенду. 
    *   `Host $host`: Передает оригинальный заголовок хоста (например, `api.chabupelik.su`).
    *   `X-Real-IP $remote_addr`: Передает реальный IP-адрес посетителя сайта, а не IP-адрес самого прокси.
    *   `X-Forwarded-For`: Передает цепочку IP-адресов, через которые прошел запрос.
    *   `X-Forwarded-Proto $scheme`: Передает протокол (HTTP или HTTPS).
*   `client_max_body_size 50M`: Защита от ошибок `413 Request Entity Too Large`. Позволяет Nginx пропускать файлы размером до 50 мегабайт (нужно для загрузки качественных фото сельхозтехники).
*   `proxy_buffering on / off`: Включает или выключает буферизацию ответов. Для статических картинок (`/media/`) буферизация включена для стабильного стриминга файлов, а для API (`/api/`) — выключена для моментального ответа.
*   `proxy_cache_valid 200 24h` и `expires 24h`: Говорит Nginx сохранять (кэшировать) успешные ответы с кодом `200` на 24 часа. При повторном открытии картинки трактора Nginx отдаст ее мгновенно из своего кэша, вообще не задействуя контейнер MinIO и экономя ресурсы процессора.

    *   **Зачем:** Смотреть логи (вывод питоновских принтов, логов и ошибок) нашего FastAPI в реальном времени. Нажми `Ctrl + C` для выхода.

    *   **Зачем:** Быстро переименовать сообщение самого последнего (локального) коммита, если допустил опечатку.
*   `git reset --soft HEAD~1`
    *   **Зачем:** Безопасно удалить последний коммит. Сам коммит сотрется, но все изменения в файлах сохранятся (код не пропадет). Полезно, если нужно дописать код и закоммитить заново.
*   `git reset --hard HEAD~1`
    *   **Зачем:** Жестко удалить последний коммит и НАЧИСТО стереть все изменения в файлах. Возвращает код к состоянию предыдущего коммита. *Внимание: изменения будут безвозвратно потеряны!*
*   `git push origin main --force`
    *   **Зачем:** Принудительно протолкнуть изменения на GitHub (использовать после `--amend` или `reset`, чтобы обновить историю на самом GitHub). *Безопасно только при одиночной разработке в приватной ветке!*

# ЧАСТЬ II: ФРОНТЕНД-ИНФРАСТРУКТУРА (VUE 3 + VITE)

## 1. Системная архитектура клиентской части (SPA)

### 1.1 Стек технологий и сборка
*   **Фреймворк:** Vue 3 (Composition API, `<script setup>`, использование хуков-composables) — обеспечивает максимальную производительность, переиспользуемость и читаемость логики компонентов.
*   **Сборщик (Bundler):** Vite — гарантирует мгновенный запуск локального dev-сервера и высокооптимизированную компиляцию продакшен-бандла.
*   **Маршрутизация (Routing):** Vue Router 4 с поддержкой HTML5 History Mode и метаданных для ролевой модели.
*   **Управление состоянием (State Management):** Pinia — реактивное хранилище глобального состояния (токены, данные авторизованного пользователя).
*   **Стилизация (CSS Framework):** Tailwind CSS — Utility-first фреймворк для быстрой и строгой верстки интерфейсов.
*   **HTTP-клиент:** Axios — с настроенными перехватчиками (Interceptors) для автоматического прикрепления JWT-токена и умного обновления сессии.

### 1.2 Адаптивный дизайн и UI/UX (Mobile-First)
Разработка интерфейса ведется по принципу Mobile-First. Весь функционал сайта и административной панели должен быть на 100% доступен и удобен на смартфонах и планшетах:
*   **Универсальная сетка (Grid/Flexbox):** Карточки сельхозтехники на главной странице и в каталоге автоматически перестраиваются: от 1 колонки на смартфонах до 4 колонок на ультрашироких экранах.
*   **Навигация (Burger Menu):** На десктопе в хедере отображается классическое меню. На мобильных устройствах меню сворачивается в иконку "гамбургера", открывающую боковую панель (Drawer).
*   **Индикация загрузки (Skeleton System):** Вместо классических лоадеров при загрузке данных с API (каталог техники, таблицы в админке) используются компоненты-скелетоны (`Skeleton.vue`), предотвращающие "прыжки" контента и улучшающие UX.
*   **Адаптивная админ-панель:** Системные таблицы реализованы через переиспользуемый компонент `DataTable.vue`, который в мобильном представлении перестраивается в блочный формат (Card-based layout) или получает горизонтальный скролл.

### 1.3 Архитектура безопасности и стабильности
*   **Code Splitting (Ленивая загрузка):** Исходный код физически разделяется сборщиком Vite на разные JS-файлы (чанки). Логика административной панели (`/admin/*`) вынесена в изолированный чанк.
*   **Изоляция состояния (Pinia Security):** `Access Token` хранится исключительно в оперативной памяти (в стейте Pinia) и уничтожается при закрытии вкладки. 
*   **Модульные Navigation Guards:** Логика защиты маршрутов вынесена из файла роутера в отдельный слой `guards/`. Функции `authGuard` и `roleGuard` проверяют наличие сессии и соответствие роли, сохраняя файл роутера чистым.
*   **Глобальный перехват ошибок (Error Boundary & Mapper):**
    *   Реализован через `app.config.errorHandler` во Vue 3 (перехват падений компонентов с отображением Fallback UI).
    *   **API Error Layer:** Внедрен централизованный сервис `apiErrors.js` (Error Mapper). Любая ошибка от бэкенда (400, 422, 500) перехватывается, трансформируется в читаемый для пользователя текст и отправляется в глобальный `useToast`, исключая разрозненные `console.log` по проекту.

### 1.4 Глобальная ENV конфигурация фронтенда (Config Layer)
Для обеспечения гибкости и подхода White Label, все юридические и контактные данные вынесены в переменные окружения `.env`. Для предотвращения размазывания `import.meta.env` по всему проекту внедрен слой `config/index.js`, который централизованно считывает, нормализует и экспортирует эти переменные.

## 2. Спецификация интеграции и управления данными (Domain & State)

Для предотвращения рассинхронизации данных и хаоса в бизнес-логике на фронтенде вводятся строгие архитектурные контракты:

### 2.1 Контракт API-ответов
Фронтенд ожидает от бэкенда строго типизированные ответы:
*   **Success Response:** `{"status": "ok", "data": ...}`
*   **Paginated Response:** `{"status": "ok", "total": X, "limit": Y, "offset": Z, "data": [...]}`
*   **Error Response:** `{"status": "error", "message": "Очеловеченный текст", "details": [...]}`
*Эта жесткая структура позволяет `apiErrors.js` универсально парсить ошибки для всего приложения.*

### 2.2 Стратегия синхронизации (Server State vs Client State)
*   **Источник истины:** Бэкенд всегда является единым источником истины. Pinia используется **только** для Client State (токены, тема оформления, открытые окна). Списки лидов и техники (Server State) не кэшируются в Pinia.
*   **Стратегия обновления UI (Pessimistic vs Optimistic Updates):**
    *   *Pessimistic Update (Пессимистичное обновление):* Применяется для критичных данных (создание лида, удаление пользователя). UI показывает загрузчик и меняется **только после** успешного ответа сервера `2xx`. При успехе вызывается функция `refetch()` для полной перезагрузки списка с сервера.
    *   *Optimistic Update (Оптимистичное обновление):* Применяется для UX-чувствительных действий (например, смена статуса лида на `IN_PROGRESS`). Интерфейс меняется мгновенно (цветной бейдж меняется на глазах), запрос уходит в фоне. Если сервер возвращает ошибку, UI незаметно "откатывается" к предыдущему состоянию, а менеджер получает уведомление через Toast.

### 2.3 Слой бизнес-правил (Domain Rules Layer)
Бизнес-логика (например, "может ли редактор удалить машину" или "какие статусы доступны для перехода") не должна хардкодиться внутри Vue-компонентов. Вся подобная логика выносится в отдельные функции-хелперы в папке `src/domain/` (например, `src/domain/lead.domain.js`), что позволяет переиспользовать правила валидации в формах, таблицах и модальных окнах.

### 2.4 Взаимодействие с API (Axios + Refresh Lock Flow)
Для обеспечения механизма «Скользящей сессии» (Rolling Refresh) реализован паттерн перехватчиков (Interceptors) с защитой от состояния гонки:
1.  **Request Interceptor:** Axios автоматически извлекает `Access Token` из Pinia и подставляет его в заголовок `Authorization`.
2.  **Response Interceptor & Refresh Queue Lock:** Если бэкенд возвращает статус `401 Unauthorized` (токен протух), а клиент делает сразу 10 параллельных запросов, первый упавший запрос включает блокировку (Refresh Lock). Все последующие запросы ставятся в очередь (Promise Queue) до получения нового токена от эндпоинта `/refresh`, после чего выполняются одновременно. Интерфейс не прерывается.

### 2.5 Наблюдаемость фронтенда (Frontend Observability)
*   Любая непредвиденная ошибка, перехваченная через `app.config.errorHandler`, не просто выводится в консоль, а логируется в массив `errorQueue` в оперативной памяти с метаданными (путь, время, stack trace). В будущем это позволяет легко подключить отправку отчетов об ошибках (Sentry / GlitchTip) на сервер без переписывания архитектуры.

## 3. Структура маршрутизации (Vue Router)

Проект разделен на две логические зоны: Публичную (Public) и Административную (Private).

### 3.1 Публичные маршруты (Public Layout)
Используют общий шаблон (Header, Footer).
*   **`/` (Главная страница):** Лендинг с секциями (Hero, About, Популярная техника, Форма заявки).
*   **`/machines`:** Каталог техники (серверная пагинация, скелетоны при загрузке).
*   **`/machines/:id-:slug`:** Детальная карточка конкретной модели техники. URL формируется динамически (например, `/machines/15-john-deere-8r`) для улучшения SEO.
*   **`/policy` / `/terms`:** Статические юридические страницы. Отображение реализовано через рендер статических `.md` (Markdown) файлов.
*   **`/:pathMatch(.*)*` (Not Found 404):** Страница с ошибкой 404, перехватывающая все несуществующие публичные маршруты.

### 3.2 Административные маршруты (Admin Layout)
Доступ строго по JWT и ролям (защищены через `guards/`).
*   **`/login`:** Страница авторизации.
*   **`/admin/leads` (Управление заявками):** Интерактивная таблица входящих лидов (`SUPERADMIN`, `MANAGER`).
*   **`/admin/machines` (Редактор техники):** Таблица-каталог техники (`SUPERADMIN`, `EDITOR`). Поддержка `multipart/form-data` для загрузки изображений в MinIO.
*   **`/admin/users` (Управление персоналом):** Интерфейс создания, блокировки и удаления учетных записей (`SUPERADMIN`).
*   **`/admin/audit` (Журнал аудита):** Просмотр логов системы с продвинутой фильтрацией и серверной пагинацией (`SUPERADMIN`).
*   **`/403` (Forbidden 403):** Экран "Недостаточно прав".
