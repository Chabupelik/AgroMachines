# Системная архитектура проекта:

## 1. Сетевая инфраструктура и деплой

*   **Cloudflare (Proxy Mode - Оранжевое облако):**
    *   **Скрытие IP:** Запросы идут через прокси-серверы Cloudflare, скрывая реальный IP-адрес хостинга от DDoS-атак и сканирования портов.
    *   **WAF (Web Application Firewall):** Автоматическая фильтрация вредоносного трафика, блокировка известных эксплойтов и подозрительных юзер-агентов.
    *   **Rate Limiting:** Ограничение частоты запросов на уровне DNS для публичного эндпоинта `/api/callback` (например, максимум 3 запроса в минуту с одного IP) для защиты от спама.
*   **Nginx (Reverse Proxy и Веб-сервер):**
    *   **Раздача фронтенда:** Локальный Nginx на сервере напрямую отдает собранный статический бандл Vue 3 (HTML, CSS, JS). Конфигурация включает правило `try_files $uri $uri/ /index.html;` для корректной работы роутинга.
    *   **Проксирование API:** Запросы на `/api/` перенаправляются на локальный порт Python-приложения (например, `http://127.0.0.1:8000`).
    *   **Проксирование медиафайлов (MinIO):** Запросы на `/media/` (или адрес бакета) проксируются на порт локального S3-хранилища MinIO (например, `http://127.0.0.1:9000`). Это исключает необходимость открывать порты MinIO наружу и гарантирует, что все медиафайлы отдаются через Nginx под защитой Cloudflare.
    *   **Безопасность заголовков:** Настройка заголовков безопасности, таких как HSTS, `X-Frame-Options: DENY` (защита от Clickjacking) и `Content-Security-Policy`.

## 2. Архитектура Frontend (Vue 3 + Vite)

*   **Разделение бандлов (Code Splitting):**
    *   Публичная часть (витрина сельхозтехники, форма заявки) и панель администратора (`/admin`) физически разделены на уровне чанков (через динамический импорт в Vue Router). Обычный пользователь не загружает JS-код, содержащий административную логику.
*   **Управление состоянием (State Management):**
    *   Использование Pinia для централизованного хранения токенов авторизации и состояния сессии администратора.
*   **Интеграция безопасности:**
    *   Интеграция невидимого виджета Cloudflare Turnstile в форму отправки заявки на фронтенде.

## 3. Архитектура Backend (Python / FastAPI)

*   **Асинхронный движок (Asyncio):**
    *   Использование FastAPI в асинхронном режиме. Это позволяет обрабатывать большое количество одновременных соединений (включая вебхуки от Telegram) без блокировки основного потока выполнения.
*   **Работа с СУБД:**
    *   СУБД PostgreSQL в связке с асинхронным драйвером и ORM SQLAlchemy 2.0 (использование `asyncSession`).
*   **Контроль версий базы данных (Миграции через Alembic):**
    *   Отказ от автоматического создания таблиц при старте. Все изменения структуры БД описываются декларативно в моделях SQLAlchemy и накатываются на сервер в виде пошаговых миграций с помощью утилиты Alembic.
*   **Абстракция объектного хранилища (MinIO / S3):**
    *   Для хранения медиафайлов (фотографий техники) используется S3-совместимый протокол (через библиотеку `boto3`). Физически файлы хранятся в локальном контейнере **MinIO** на том же сервере. Это позволяет писать Cloud-Native код и в любой момент переключиться на внешнее облако (Cloudflare R2, AWS S3) простой заменой переменных окружения, без переписывания логики.
*   **Фоновые задачи (Background Tasks):**
    *   Для отправки уведомлений в Telegram-бот используется встроенный в FastAPI механизм BackgroundTasks. Бекенд мгновенно сохраняет заявку в БД и отдает клиенту ответ 200 OK, а отправка сетевого запроса к серверам Telegram выполняется асинхронно в фоне, не блокируя пользователя.
*   **Многофункциональный кэш-слой (Redis):**
    *   Внутрисистемная память Redis используется расширенно: не только для лимитирования запросов (Rate Limiting), но и для временного кэширования ресурсоемких выборок каталога техники (`machines`), хранения временных сессий, распределенных блокировок и буферизации фоновых процессов.
*   **Валидация и парсинг (Pydantic):**
    *   Строгая валидация входящих и выходящих данных с помощью схем Pydantic.
*   **Конфигурация и секреты (Pydantic Settings):**
    *   Все конфигурационные данные (токен бота, реквизиты доступа к БД, секретный ключ JWT, доступы к MinIO) хранятся в изолированном файле `.env`. Чтение и валидация переменных окружения осуществляются через класс Settings библиотеки `pydantic-settings`, предотвращая запуск приложения с некорректными или отсутствующими параметрами.

## 4. Спецификация безопасности API

### А. Публичная форма обратного звонка

*   **Интеллектуальная валидация номера телефона:** Вместо базовых регулярных выражений на этапе парсинга Pydantic-схемой применяется библиотека `phonenumbers` (порт Google Libphonenumber). Проводится проверка не только формата записи, но и существования кода оператора и страны для автоматического отсечения заведомо вымышленных и нераспределенных диапазонов цифр.
*   **Санитаризация текстовых полей:** Принудительное удаление HTML-тегов, скриптов и спецсимволов из текстовых полей перед сохранением данных для предотвращения XSS-инъекций.
*   **Предотвращение дублирования (Активные заявки):** При поступлении нового запроса выполняется предварительный поиск в БД по номеру телефона среди записей со статусами `NEW` или `IN_PROGRESS`. 
    *   При обнаружении активной заявки новая запись в БД не создается, а клиенту возвращается статус-ответ `already_exists`, который Vue отображает в виде дружелюбного сообщения. Это защищает базу от дублирования, а Telegram-канал менеджеров — от повторного шума.
*   **Капча (Turnstile):** Проверка токена Cloudflare Turnstile на стороне бекенда перед фиксацией лида для блокирования автоматизированных бот-сетей.
*   **Многоуровневый Rate Limiting (Redis):** Ограничение частоты отправки запросов с одного IP-адреса и масок подсетей с использованием Redis. Реализуется алгоритм Token Bucket для защиты от целенаправленного ручного спама и перебора номеров.

### Б. Авторизация администратора (JWT + Cookie с механизмом Rolling Refresh)

Для обеспечения максимальной безопасности сессий администратора применяется раздельная двухтокенная схема авторизации:

1.  **Access Token (JWT в ОЗУ клиента):**
    *   **Время жизни:** Краткосрочный (15 минут).
    *   **Передача:** Возвращается сервером в теле JSON-ответа при успешной авторизации и сохраняется Vue-приложением в оперативной памяти (в стейте Pinia). Он прикрепляется к каждому HTTP-запросу в заголовке `Authorization: Bearer <token>`.
    *   **Защита:** Access Token не хранится в LocalStorage или SessionStorage, что исключает его компрометацию через прямое чтение постоянного хранилища браузера после завершения сессии или закрытия вкладки.
2.  **Refresh Token (HttpOnly Cookie на клиенте):**
    *   **Время жизни:** Долгосрочный (7 дней).
    *   **Передача:** Записывается сервером в браузер через заголовок `Set-Cookie` с флагами `HttpOnly`, `Secure` и `SameSite=Strict`. Браузер автоматически прикрепляет эту куку к запросам обновления сессии (`POST /api/refresh`).
    *   **Защита уровня HttpOnly:** Флаг `HttpOnly` полностью блокирует доступ к куке со стороны JavaScript. Никакой вредоносный скрипт на клиенте не может прочитать этот токен через `document.cookie`.
    *   **Защита уровня Secure (HTTPS):** Флаг `Secure` гарантирует, что браузер передаст эту куку только по зашифрованному HTTPS-соединению, исключая перехват в открытой сети (защита от MITM-атак).
    *   **Защита SameSite=Strict:** Предотвращает уязвимость CSRF (межсайтовая подделка запроса), блокируя отправку куки при запросах со сторонних сайтов.
3.  **Хеширование паролей (Argon2id):**
    *   Для обеспечения криптостойкости паролей администраторов на бэкенде применяется алгоритм **Argon2id** (рекомендованный OWASP и побеждавший на Password Hashing Competition). Данный алгоритм обеспечивает лучшую на текущий момент защиту от брутфорса, в том числе с использованием графических процессоров (GPU) и специализированных интегральных схем (ASIC), за счет контролируемого использования ресурсов процессора и оперативной памяти.
4.  **Механизм скользящей сессии (Rolling Refresh Tokens):**
    *   Для обеспечения комфортного UX и надежной защиты применяется концепция «скользящего» токена.
    *   При каждом обновлении сессии через `/api/refresh` (раз в 15 минут) бекенд проверяет старый Refresh-токен, выдает новый короткий Access-токен и **перевыпускает** долгосрочный Refresh-токен, сдвигая его срок жизни еще на 7 дней вперед.
    *   **Результат:** Если менеджер заходит в админку хотя бы раз в неделю, его сессия продлевается автоматически и бесконечно. Если менеджер не проявляет активности более 7 дней (например, ушел в отпуск), Refresh-токен окончательно сгорает, и при следующем визите система безопасно потребует повторный ввод пароля.
5.  **Ролевая модель доступа (RBAC):**
    *   В JWT-токен пользователя записывается его роль (`SUPERADMIN`, `EDITOR`, `MANAGER`), на основе которой бэкенд строго разграничивает доступ к эндпоинтам:
        *   `SUPERADMIN` (Главный администратор): Полный доступ ко всем ресурсам (управление техникой, заявками, пользователями).
        *   `EDITOR` (Редактор контента): Доступ только к CRUD-операциям над таблицей техники (`machines`).
        *   `MANAGER` (Менеджер по продажам): Доступ только к чтению и обновлению входящих заявок (`leads`).
    *   *Замечание для защиты:* Данная архитектура предусматривает масштабирование ролевой модели и добавление новых типов пользователей без необходимости перепроектирования схемы авторизации.

## 5. Интеграция с Telegram-ботом

*   **Двустороннее управление:**
    *   **Оповещение:** При создании нового лида бекенд отправляет сообщение в рабочий чат менеджеров.
    *   **Интерактивные Inline-кнопки:** Сообщение в Telegram содержит кнопки «Взять в работу» и «Завершить».
    *   **Оптимистическая блокировка лидов (Защита от гонки состояний):** Чтобы предотвратить ситуацию, когда два менеджера одновременно нажимают кнопку «Взять в работу» на одном и том же сообщении, обновление статуса заявки в СУБД производится атомарно с жестким логическим условием: `UPDATE leads SET status = 'IN_PROGRESS', updated_at = NOW() WHERE id = :id AND status = 'NEW'`. Если запрос затронул 0 строк, бэкенд фиксирует конфликт (лид уже был обработан другим сотрудником), прерывает операцию и возвращает предупреждение.
    *   **Webhook-архитектура:** Нажатие на кнопку в Telegram отправляет callback-запрос на эндпоинт бэкенда `/api/tg/webhook`. Бэкенд принимает этот запрос, обновляет статус лида в базе данных PostgreSQL и редактирует исходное сообщение в Telegram для отображения актуального статуса заявки (например, меняет кнопку на текст «В работе у @username»).

## 6. Концептуальная схема Базы Данных (PostgreSQL)

*   **Таблица `users` (Администраторы):**
    *   `id` (UUID, primary key)
    *   `username` (String, unique, indexed)
    *   `password_hash` (String) — *Пароль хешируется с использованием Argon2id с индивидуальной солью.*
    *   `role` (Enum: `SUPERADMIN`, `EDITOR`, `MANAGER`) — *Определяет уровень прав доступа пользователя в системе.*
    *   `is_active` (Boolean)
*   **Таблица `machines` (Карточки сельхозтехники):**
    *   `id` (Integer, primary key)
    *   `title` (String, indexed)
    *   `description` (Text)
    *   `specifications` (JSONB, для гибкого хранения характеристик техники)
    *   `price` (Numeric)
    *   `image_url` (String) — *Вместо локального пути хранится URL-адрес объекта, проксируемый Nginx из локального MinIO бакета.*
    *   `created_at` (DateTime)
*   **Таблица `leads` (Заявки на обратный звонок):**
    *   `id` (Integer, primary key)
    *   `client_name` (String)
    *   `client_phone` (String, indexed)
    *   `status` (Enum: `NEW`, `IN_PROGRESS`, `DONE`) — *Обновление статуса защищено атомарной логикой для избежания конфликтов между менеджерами.*
    *   `created_at` (DateTime)
    *   `updated_at` (DateTime)
*   **Таблица `audit_logs` (Журнал аудита действий):**
    *   `id` (Integer, primary key)
    *   `user_id` (UUID, foreign key -> `users.id`, либо `null`, если действие выполнил Telegram-бот)
    *   `action` (String — например, `CREATE_MACHINE`, `UPDATE_PRICE`, `CHANGE_LEAD_STATUS`)
    *   `entity_type` (String — `machine`, `lead`)
    *   `entity_id` (Integer)
    *   `timestamp` (DateTime, indexed) — *Позволяет детально отследить, кто, когда и что именно изменил в системе, что критически важно для контроля действий менеджеров и автоматики.*

## 7. Стратегия резервного копирования (Backup Strategy)

Для обеспечения непрерывности бизнес-процессов, защиты от аппаратных сбоев на сервере и минимизации рисков потери критически важных данных в системе реализована регулярная стратегия резервного копирования:

*   **Автоматический дамп Базы Данных (PostgreSQL):** Раз в сутки в автоматическом режиме с помощью планировщика выполняется резервное копирование структуры и данных базы данных с помощью стандартной утилиты `pg_dump` с последующим архивированием (`gzip`).
*   **Резервное копирование медиафайлов (MinIO):** Раз в сутки запускается автоматический скрипт синхронизации медиа-бакетов MinIO (фотографии техники), обеспечивающий консистентность файлов и записей в БД.
*   **Политика хранения и ротации:** Все созданные резервные копии шифруются и сохраняются во внешнее изолированное хранилище (например, выделенный бэкап-сервер) с глубиной хранения (Retention) от 7 до 30 дней. Это исключает риски потери данных в случае физического уничтожения основного сервера.
